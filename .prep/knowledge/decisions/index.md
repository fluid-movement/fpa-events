## Entries

* [Backups are Hetzner's VPS backups; no per-app database backup](/decisions/01M57FTWF3ZR0A2JYQ66TVTABT.md) - Production runs on a Hetzner VPS managed by Coolify, and Hetzner's paid VPS backups cover the whole server, Postgres included. Decided with the user on 2026-10-18 that this is a good enough backup strategy for now: no Coolify scheduled Postgres backup and no off-box S3 copy. Revisit if point-in-time recovery or a faster restore is ever needed.
* [Error tracking runs on self-hosted GlitchTip](/decisions/01M57G90Y5GDVT34B6CNE6M6XR.md) - Sentry-protocol events go to a self-hosted GlitchTip on the Hetzner/Coolify box, not Sentry SaaS. Decided with the user on 2026-10-18: GlitchTip is the lightest Sentry-compatible self-hosted tracker, the official Sentry SDKs work unchanged (only the DSN differs), and it has a built-in MCP server so agents can read errors. Data stays on our server, so it is not a third-party processor, and it is covered by the Hetzner VPS backups.
* [Pin the deploy to an exact Node 22 release](/decisions/01M57G911WCPZM7AGP2Q3ZJQ30.md) - NIXPACKS_NODE_VERSION is pinned to an exact Node 22 release matching the dev machines, not moved to Node 24. Decided with the user on 2026-10-18.
* [Laravel goes into maintenance mode during the final migration](/decisions/01M57G914YAPXEZJNSRR2EHF2Y.md) - The legacy Laravel app is put in maintenance mode before the final dump so no new data lands in it afterwards. Decided with the user on 2026-10-18.
* [No redirects for legacy Laravel URLs](/decisions/01M57G91830K475ZMFTVTCY8VY.md) - Old Laravel paths are not redirected after the switch; renamed pages simply 404, event ids keep their path shape. Decided with the user on 2026-10-18.

* [Follow SvelteKit 3 idioms](/decisions/01M57N60ZTE7RBG04JEDQEA4RD.md) - The app is on SvelteKit 3, so code and reviews follow Kit 3 idioms ($app/env, $app/env/private|public, hook types from @sveltejs/kit/hooks, options through sveltekit(...) in vite.config.ts, #lib imports, no Kit 2 patterns from older docs). Stated by the user on 2026-10-18; new dependencies must also declare Kit 3 in their peer range.
* [Error reports carry no breadcrumbs and no request data](/decisions/01M57N612M4A7WRSDN0HW0EMY2.md) - Reports to GlitchTip drop every breadcrumb, the whole request object and the url tag, keep the user as an id only, and keep a transaction name only when it is a route id, because calendar-feed and invite URLs carry credentials in the path. The public DSN is a build arg as well as runtime env, since the CSP connect-src is fixed at build time. Source-map upload targets org fpa, project events-new and runs only when SENTRY_AUTH_TOKEN is set.
* [Error reports allowlist database error text instead of redacting it](/decisions/01M57R12DXKFJBJPPTFW5G6M2B.md) - Decided 2026-10-18 after two failed reviews of a pattern-based redactor. Postgres writes user-controlled values into error messages unescaped (a value can contain quotes and parentheses), so no pattern list can promise to remove them. Sentry's own data-scrubbing guidance gives three layers (SDK-side filtering, server-side scrubbing, a Relay) and prefers keeping data out of the SDK; GlitchTip offers only the SDK layer. So for any PostgresError the event keeps the error type, the SQL state code, the constraint name and the stack, and drops the message and detail; for a DrizzleQueryError it keeps the SQL text up to its params: tail and drops the rest. Other errors keep their message. Everything earlier still holds: no breadcrumbs, no request data, the user as an id only, route id as transaction, no extra, span data or frame variables.
* [Deleting an account requires the current password](/decisions/01M57TAMX19MSS5AHP4XHHJT53.md) - Account deletion asks for the current password in the dialog, not a fresh sign-in; a wrong password deletes nothing. The field is named _password so SvelteKit 3 does not echo it back on a failed submission. Verified through Better Auth's configured verifier, so legacy bcrypt hashes work. Default chosen by the agent on 2026-10-18 and not contradicted by the user.
* [Token-bearing routes emit no og:url](/decisions/01M57TS96FDXQQHEQDAAMFQDS6.md) - Link-preview tags use the request origin plus path for og:url, but routes whose path carries a credential (currently /invite) omit it, kept in TOKEN_ROUTE_PREFIXES in src/lib/utils/meta.ts, so a token never lands in a canonical-URL tag that crawlers and search engines read. The query string is never included, which already covers reset-password. Add any new token-in-path route to that list. Decided by the agent on 2026-10-18 after review.
* [Deleting an account deletes the events it created, co-organized or not](/decisions/01M57VEKVEN9NWMNNJQAVT280Q.md) - No ownership transfer: when a user deletes their account, every event they created is deleted, even if it has co-organizers, as today. Decided by the user on 2026-10-18 ("events are just deleted"). The remaining fix is that the pictures of those events are released from R2, as deleteEvent does.
* [Picture release never blocks account deletion](/decisions/01M57WDACR8E3KV0YT54GHJ6QG.md) - deleteAccount releases the pictures of the deleted events through releaseEventPictures in src/lib/server/eventForm.ts, after the event rows are deleted and before the verification and user deletes. The function is best-effort and cannot throw to its caller: each event is guarded separately, so an R2 failure or a failing 'picture used elsewhere' query never leaves an account half-deleted, and a leftover object is cheaper than a failed erasure. Pictures shared with another user's event stay. Chosen by the agent and confirmed by review on 2026-10-18. Gap: no test fails if the call is removed from the handler, since R2 keys are blank in tests.
* [No external uptime monitor](/decisions/01M59PDF3FDWGGK29GAK9ERABM.md) - Coolify's container health check on /healthz is the only uptime wiring; no external uptime monitor or second service. Coolify already emails the maintainer when it is down, and this is not an enterprise-grade application. Decided by the user on 2026-10-19, relaxing the earlier requirement for a check outside the Hetzner box (a dead server stays silent only if Coolify's own alert is silent too).
* [Pin the deploy to Node 24](/decisions/01M59PK8QMF1B7Z8BMMDMD6PH5.md) - NIXPACKS_NODE_VERSION is pinned to 24 in Coolify, replacing the earlier decision to pin an exact Node 22 release. It already builds and runs on 24 (deploy 0wotsqcti… of 2026-10-18 passed its /healthz check) and the dev machines run Node 24. 24 is a major-only pin, so the patch release moves with the nixpacks resolver; SvelteKit 3 needs >=22.17, which every Node 24 clears. Decided by the user on 2026-10-19.
* [Request origin comes from proxy headers, not paths.origin](/decisions/01M5A2XJ7R7G055E9GYKMS8CC7.md) - adapter-node 6 ignores ORIGIN, and nothing sets paths.origin. The deployed app instead takes its public https origin from the proxy via the HOST_HEADER and PROTOCOL_HEADER env vars set in Coolify. Verified on events-dev.fluid-movement.de on 2026-10-19: sign-in, password reset, email verification and an RSVP through a remote-function form all succeeded, so the cross-site check accepts the requests. Re-check after the switch to events.freestyledisc.org, since the headers are per-app Coolify env.
* [Better Auth needs no advanced.ipAddress setting](/decisions/01M5A2XJC28ZGAW405A88YKK8E.md) - Behind Coolify's proxy, the session.ip_address Better Auth stores is the visitor's real address: on 2026-10-19 events-dev recorded 2001:0a61:04be:7f01:: for a visitor whose IPv6 address was 2001:a61:4be:7f01:25a8:5756:c07c:44f1. Better Auth truncates IPv6 addresses to the /64 prefix, so the lower 64 bits are always zero and users on one /64 share a rate-limit bucket. No Cloudflare is planned in front, so the default header handling stays. Revisit if a CDN or another proxy is ever added.
* [Audit findings become child issues of the audit area](/decisions/01M5A3G5EMHG5FRY0CANFPSXN2.md) - An agent auditing one area files each finding it does not fix on the spot as a new issue under that area's audit issue (tag security, kind matching the work, requirement stating the vulnerability, where it is and how to reproduce it, acceptance stating the fix and a regression test where the testing rules call for one). A finding fixed in place is logged on the audit issue instead. Findings are never left only in a report or the conversation. Which findings block go-live is decided by the user, per finding; the filing agent states its severity and says whether it thinks the finding blocks. Decided by the user on 2026-10-19.
