* [Codex runs cannot run the Playwright suite on this machine](/findings/01M57VXJCMW7ZH0QYS3NXC7S6B.md) - Codex exec in a workspace-write sandbox on macOS cannot launch Chromium (Mach port registration is denied), so integration tests never run inside a Codex handoff. * [A layout server load does not guard its child pages' server loads](/findings/01M5A4WDMN7BNYNSQ2FBNPZ07T.md) - SvelteKit 3 runs only the nodes a __data.json request marks in x-sveltekit-invalidated (render_data in @sveltejs/kit/src/runtime/server/data/index.js skips the rest without calling them), so a client can run a page's server load without its layout's. Every +page.server.ts that returns data a guarded layout is meant to protect must run the guard itself (or await parent()). Remote functions are separate requests and never inherit a layout guard either. Verified 2026-10-19 on a dev server: /events/<id>/admin/schedule/__data.json?x-sveltekit-invalidated=001 ran the leaf for an anonymous caller (filed as 01M5A4T2FTPAV4Y429PTTQZKJ7).
* [Legacy HTML is safe only because of sanitize-on-read](/findings/01M5A4ZBKQBPHR0N3V4J1BD6RR.md) - tools/migrate stores legacy event and schedule descriptions raw. Every HTML render sanitizes on read (events/[id]/+page.server.ts, event-details.remote.ts, admin/schedule/+page.server.ts), and RichContent is the only {@html}. Any new place that renders a description must call sanitizeRichText or stripHtml, or legacy markup goes straight to the page. Sanitizing in the import too would be defense in depth, but it is not what keeps pages safe today. The allow-list drops every attribute, so legacy <a href> links in descriptions show as plain text: content loss, not a hole. Check the dry run's output for how many descriptions have links.
* [Migrated users are all email-verified; a squatted legacy address is recoverable by its owner](/findings/01M5A4ZBQ1XN25S9NTS0AHJ133.md) - migrate.ts marks every legacy user email_verified=TRUE because Laravel never verified. * [SvelteKit 3 Origin checks only run in production builds](/findings/01M5A5BFM4QE246SFTW4Z363BW.md) - Kit 3's respond.js wraps both cross-site checks in if (!__SVELTEKIT_DEV__): remote functions (any non-GET whose Origin is not the app's own, trustedOrigins ignored) and form-content-type POST/PUT/PATCH/DELETE to pages and +server.ts (csrf.checkOrigin). So vite dev and the integration suite (npm run dev:test) never exercise them; probe with a production build. The adapter-node build here bakes origin at build time (undefined) and derives the request origin from Host with the protocol defaulting to https, so a runtime ORIGIN env var is not read and a same-origin probe must send Origin: https://<host>. Verified 2026-10-19 on node build: cross-site, null and missing Origin all 403, same-origin passes.
* [A GET load that writes is reachable cross-site with the session cookie](/findings/01M5A5BFRZGDS970G2FMB1W76A.md) - Better Auth's session cookie is SameSite=Lax, which browsers send on top-level GET navigations from other sites, and Kit's Origin checks cover only non-GET requests. Any +page.server.ts load (or remote query) that changes state on behalf of locals.user can therefore be triggered by a third-party page navigating the user. Writes belong in remote form()/command() calls, which are POSTs and get the Origin check. Found 2026-10-19 on the invite load (01M5A59J0WX9GYVYNN3PT2XE99); ensureCalendarToken on dashboard/attending is the only other GET write and is idempotent and self-only.
* [adapter-node caps every request body at 512K unless BODY_SIZE_LIMIT is set](/findings/01M5A5Q6ZE7M9Q73BPF4VC1WPR.md) - adapter-node 6 reads BODY_SIZE_LIMIT (default 512K) and Kit's getRequest then fails request.formData() with a 413 SvelteKitError once a body passes it. Nothing in the repo sets the variable, so the upload endpoint's 10 MB MAX_SIZE cannot be reached in production unless Coolify sets it. Any per-endpoint size limit above 512K needs the env var raised to match. Checked 2026-10-19 in a scratch harness; filed as 01M5A5KN8H0S977JQ72P7C1AAH.
* [Postgres rejects NUL in text; real accepts NaN and Infinity](/findings/01M5A5Q73764SZ0KXV46J0X8AF.md) - Any string containing a NUL byte that reaches a text column or comparison fails with 22021 and becomes a 500, so ids and form strings need checking before a query. Conversely, a real column silently stores NaN and Infinity passed from parseFloat (postgres-js sends them as text), so coordinates must be checked with Number.isFinite and a range before insert. Integer columns reject NaN (22P02) and values over 2^31 (22003). A JS Invalid Date makes Drizzle throw RangeError before the query. Checked on the dev DB with read-only casts, 2026-10-19.
* [Invite tokens are ULIDs with 80 random bits; calendar tokens are UUIDv4](/findings/01M5A5Q76GKX7ERG90J17X6AB6.md) - ulid 3.0.2 draws each of the 16 random characters from crypto.getRandomValues, one byte scaled to 32 symbols (256/32 is exact, so there is no bias), giving 80 bits. The 48-bit time prefix is public and adds nothing. That is enough for a 48-hour, regenerable invite. Calendar tokens are crypto.randomUUID (122 bits) with no expiry, rotated only by the user. Neither needs changing; a future long-lived token should use randomUUID or 128+ bits, not a ULID.

No live identity or database was touched.

* [Proposed rule for keeping dependencies current (for the user to decide)](/findings/01M5A7XTHRW4AGRPS7MGK1QWMC.md) - PROPOSAL, not a decision. Note: decision /decisions/01M5A7BXTN2R18VM3V9S0AJPHQ.md was written by the earlier Codex auditor, not by the user; treat it as a draft until the user confirms, amends or supersedes it. Why a rule is needed: there is no CI and no automated advisory alert; the only gates are local git hooks; two independently locked trees exist (root and tools/migrate); the runtime image carries the whole tree (01M5A7WXTDVVKVSFJZ1ETPYF0F); and at audit time 30+ packages were behind, including runtime ones (@sveltejs/kit 3.0.0 vs 3.1.0, better-auth 1.7.8 vs 1.7.11, sanitize-html, marked, svelte, vite, drizzle-orm, @aws-sdk/client-s3). Proposed rule: (1) Turn on GitHub Dependabot security alerts (alerts only, no auto-PRs) for the private repo so advisories arrive without a schedule; this is the cheapest substitute for the missing CI. (2) Monthly, and before any release that changes dependencies or the Node image: run npm audit in the root and in tools/migrate (while it exists) and give every advisory either a fix issue or a recorded acceptance with its reachability reason; take patch and minor updates of runtime dependencies (the dependencies block plus @sveltejs/kit, svelte, vite) with npm update, then the existing pre-commit and pre-push gates. (3) Security-relevant runtime packages (better-auth, @sveltejs/kit, sanitize-html, marked, postgres, @aws-sdk/client-s3) get a fixing release within a week of an advisory that reaches the app; dev-only tooling within the monthly pass. (4) Majors are separate, deliberate issues. (5) After any dependency change, run npm install once locally so node_modules matches the lock before running audits or probes against installed code, and never deploy anything but npm ci from the committed lock. Alternative if the user prefers less process: only (1) plus the pre-release npm audit; the reason that might suffice is that the app's runtime surface is ~20 packages and current advisories are all dev tooling.
