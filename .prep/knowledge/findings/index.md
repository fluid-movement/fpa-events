# findings

## Entries

* [Codex runs cannot run the Playwright suite on this machine](/findings/01M57VXJCMW7ZH0QYS3NXC7S6B.md) - Codex exec in a workspace-write sandbox on macOS cannot launch Chromium (Mach port registration is denied), so integration tests never run inside a Codex handoff. Codex implementers run check, unit tests, lint and build; a Claude reviewer (or the orchestrator) runs the Playwright suite afterwards. Only one agent can use the shared test database and port 5174 at a time, so Codex prompts say not to touch them and integration runs are serialised. Observed 2026-10-18 with the better-auth upgrade.
* [A layout server load does not guard its child pages' server loads](/findings/01M5A4WDMN7BNYNSQ2FBNPZ07T.md) - SvelteKit 3 runs only the nodes a __data.json request marks in x-sveltekit-invalidated (render_data in @sveltejs/kit/src/runtime/server/data/index.js skips the rest without calling them), so a client can run a page's server load without its layout's. Every +page.server.ts that returns data a guarded layout is meant to protect must run the guard itself (or await parent()). Remote functions are separate requests and never inherit a layout guard either. Verified 2026-10-19 on a dev server: /events/<id>/admin/schedule/__data.json?x-sveltekit-invalidated=001 ran the leaf for an anonymous caller (filed as 01M5A4T2FTPAV4Y429PTTQZKJ7).
* [Legacy HTML is safe only because of sanitize-on-read](/findings/01M5A4ZBKQBPHR0N3V4J1BD6RR.md) - tools/migrate stores legacy event and schedule descriptions raw. Every HTML render sanitizes on read (events/[id]/+page.server.ts, event-details.remote.ts, admin/schedule/+page.server.ts), and RichContent is the only {@html}. Any new place that renders a description must call sanitizeRichText or stripHtml, or legacy markup goes straight to the page. Sanitizing in the import too would be defense in depth, but it is not what keeps pages safe today. The allow-list drops every attribute, so legacy <a href> links in descriptions show as plain text: content loss, not a hole. Check the dry run's output for how many descriptions have links.
* [Migrated users are all email-verified; a squatted legacy address is recoverable by its owner](/findings/01M5A4ZBQ1XN25S9NTS0AHJ133.md) - migrate.ts marks every legacy user email_verified=TRUE because Laravel never verified. So an address someone registered on the old app without owning it becomes a verified account here. The real mailbox owner cannot sign up (the address is taken), but can take the account over through password reset, which mails the address. Accepted as is: the alternative locks every legacy user out at cutover.
* [Legacy data could not be profiled; the dry run is the check](/findings/01M5A4ZBT5BARSAK07FG3K7TB0.md) - No legacy dump is restored locally (tools/migrate/.env points at fpa_legacy_test, which does not exist), the dev DB has no migrated rows, and the production DBs are firewalled. So I could not count mixed-case emails, non-image pictures, line breaks in names, non-ULID ids or link-bearing descriptions. Every finding filed under this audit is about what the code allows. The dry run of the final migration (01M4B48HENZTKHQ88QZ83E0EBH) is where to measure the real exposure.
* [SvelteKit 3 Origin checks only run in production builds](/findings/01M5A5BFM4QE246SFTW4Z363BW.md) - Kit 3's respond.js wraps both cross-site checks in if (!__SVELTEKIT_DEV__): remote functions (any non-GET whose Origin is not the app's own, trustedOrigins ignored) and form-content-type POST/PUT/PATCH/DELETE to pages and +server.ts (csrf.checkOrigin). So vite dev and the integration suite (npm run dev:test) never exercise them; probe with a production build. The adapter-node build here bakes origin at build time (undefined) and derives the request origin from Host with the protocol defaulting to https, so a runtime ORIGIN env var is not read and a same-origin probe must send Origin: https://<host>. Verified 2026-10-19 on node build: cross-site, null and missing Origin all 403, same-origin passes.
* [A GET load that writes is reachable cross-site with the session cookie](/findings/01M5A5BFRZGDS970G2FMB1W76A.md) - Better Auth's session cookie is SameSite=Lax, which browsers send on top-level GET navigations from other sites, and Kit's Origin checks cover only non-GET requests. Any +page.server.ts load (or remote query) that changes state on behalf of locals.user can therefore be triggered by a third-party page navigating the user. Writes belong in remote form()/command() calls, which are POSTs and get the Origin check. Found 2026-10-19 on the invite load (01M5A59J0WX9GYVYNN3PT2XE99); ensureCalendarToken on dashboard/attending is the only other GET write and is idempotent and self-only.
* [adapter-node caps every request body at 512K unless BODY_SIZE_LIMIT is set](/findings/01M5A5Q6ZE7M9Q73BPF4VC1WPR.md) - adapter-node 6 reads BODY_SIZE_LIMIT (default 512K) and Kit's getRequest then fails request.formData() with a 413 SvelteKitError once a body passes it. Nothing in the repo sets the variable, so the upload endpoint's 10 MB MAX_SIZE cannot be reached in production unless Coolify sets it. Any per-endpoint size limit above 512K needs the env var raised to match. Checked 2026-10-19 in a scratch harness; filed as 01M5A5KN8H0S977JQ72P7C1AAH.
* [Postgres rejects NUL in text; real accepts NaN and Infinity](/findings/01M5A5Q73764SZ0KXV46J0X8AF.md) - Any string containing a NUL byte that reaches a text column or comparison fails with 22021 and becomes a 500, so ids and form strings need checking before a query. Conversely, a real column silently stores NaN and Infinity passed from parseFloat (postgres-js sends them as text), so coordinates must be checked with Number.isFinite and a range before insert. Integer columns reject NaN (22P02) and values over 2^31 (22003). A JS Invalid Date makes Drizzle throw RangeError before the query. Checked on the dev DB with read-only casts, 2026-10-19.
* [Invite tokens are ULIDs with 80 random bits; calendar tokens are UUIDv4](/findings/01M5A5Q76GKX7ERG90J17X6AB6.md) - ulid 3.0.2 draws each of the 16 random characters from crypto.getRandomValues, one byte scaled to 32 symbols (256/32 is exact, so there is no bias), giving 80 bits. The 48-bit time prefix is public and adds nothing. That is enough for a 48-hour, regenerable invite. Calendar tokens are crypto.randomUUID (122 bits) with no expiry, rotated only by the user. Neither needs changing; a future long-lived token should use randomUUID or 128+ bits, not a ULID.
* [Authentication recovery does not revoke existing sessions](/findings/01M5A6T8D95DVNKF1GV0MTFKQ9.md) - Source review and an offline Better Auth 1.7.7 handler harness with synthetic adapter spies confirmed that reset-password calls updatePassword without deleteUserSessions, while the settings change-password call only updates the credential. auth.ts omits revokeSessionsOnPasswordReset and the page omits revokeOtherSessions. Sessions default to seven days with daily renewal. High-severity child 01M5A6NTZZ25Z46EJQ6F23G7B1 requests recovery revocation with real old-cookie regression tests; recommend fix before cutover. No live identity or database was touched.
* [Authentication response enumeration held except mixed legacy hash timing](/findings/01M5A6T8G7K72MGTW1Y4QEPMZF.md) - Unknown/wrong sign-in returned identical 401 JSON; known/unknown reset requests returned identical 200 JSON; anonymous verification resends returned identical JSON and 503/505 ms locally because the installed library applies a 500 ms floor. Signup source uses a synthetic duplicate response and dummy scrypt work. Mailgun rejection was simulated against original email source with imports stubbed: delivery errors were caught, not propagated to auth responses. Mixed bcrypt/scrypt failures remain distinguishable by work factor: 12-sample local medians 58.4 ms unknown scrypt, 57.7 ms scrypt verification, 70.3 ms bcrypt10, 278.5 ms bcrypt12. Filed low-severity 01M5A6NVDC0PNBFD30SP8KDQTV; production hash costs and network enumeration accuracy were not measured. Known-reset insert versus unknown-reset dummy read may retain small DB timing differences; the audit does not claim exact timing equality.
* [Legacy password verification is compatibility only, not transparent upgrading](/findings/01M5A6T8KC6PD0MZ29ZHWM159M.md) - src/lib/server/password.ts only verifies supported bcrypt prefixes and otherwise delegates to scrypt. The installed sign-in handler never rewrites credentials after a successful bcrypt login; the offline adapter trace only created a session. Prep product decisions require legacy passwords to keep working and do not specify rehash-on-login. Therefore the parent scope phrase transparent legacy bcrypt upgrade is an assumption to correct, not a verified defense or a new mandatory feature. Existing password.test.ts passed; timing risk is filed separately. Migration intentionally marks all imported users verified, as already documented by the upstream audit.

Installed limiter defaults are production-only memory storage, 100/10s general, 3/10s sign-in/signup/change-password and 3/60s reset/resend; offline enabled-rule probes returned 429 on the fourth call across host addresses in one IPv6 /64. No current live threshold, cookie renewal or adversarial forwarding-header probe was permitted. Widget presence proves only the public key, not the secret or Cloudflare hostname settings. package.json requests ^1.7.8 but installed better-auth/core report 1.7.7; deployment/dependency reviewers must reconcile the executable version. Parent criterion 1 stays unchecked; lock-in 01M5A6S4EXZY5WE590R1XFP6GS records the full scope and limits.
