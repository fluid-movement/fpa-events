Authentication audit lock-in, 2026-10-19 (parent 01M5A34XDWPGKSKMTVA213DHX7).

Method and limits: source review of every app authentication page, auth.ts, password.ts, email.ts, turnstile.ts, hooks.server.ts and the installed Better Auth/@better-auth/core 1.7.7 implementations. Nine existing unit tests passed (password, Turnstile, email), using a scratch Vitest config without SvelteKit/build plugins and with caches confined to the authorized scratch directory. An offline Better Auth handler harness used synthetic fixture objects, rejecting adapter stubs and mail spies: no database connections, row/account creation, real mail, or network requests. It recreated the relevant auth options; app source review established that those options match. A separate source-based email harness replaced only env/Mailgun imports to simulate rejected deliveries. These are not live database/integration results.

Passive GETs only on events-dev.fluid-movement.de: /sign-in 200 with a server-rendered data-testid="turnstile" container; /api/auth/get-session 200 null, Cache-Control: no-store, no cookie issued. HSTS and strict-origin-when-cross-origin present. The same two new-app paths on events.freestyledisc.org returned 404. No live login, attack traffic, limiter exhaustion, malformed production requests or database changes. No app server was started.

Prior lock-ins are reused, not refiled: 01M5A4W5GTV7RNJ8T4MHFVTAKJ (all route/remote guards), 01M5A4YWDG7WFE35HB9NCBWMEY (legacy hash compatibility/import, invalid/expired invites), 01M5A5B3PG61A9PBZ68BYZT3E2 (mail text, Kit CSRF, no duplicate-signup mail), 01M5A5PQ1D4BA5BF2TCJQTRV91 (garbage cookies, token URL/referrer/report protections).

Verified defenses (state how each was checked; pin application security rules, not every vendor implementation detail):

1. Wrong passwords do not authenticate under any supported hash family. src/lib/server/password.ts:6-21 handles Laravel $2y$, $2a$, $2b$ and scrypt. Existing src/lib/server/password.test.ts passed: legacy correct/wrong, bcrypt variants, scrypt correct/wrong. No duplicate compatibility tests. There is NO transparent bcrypt-to-scrypt upgrade: successful legacy handler execution only called createSession. Knowledge decisions require compatibility, not rehash-on-login. The missing upgrade is an audit-assumption correction, not a separate vulnerability; mixed-family failure timing is filed as 01M5A6NVDC0PNBFD30SP8KDQTV.

2. Skipping the UI cannot bypass email verification. src/lib/server/auth.ts:33,41-47 requires verification and sends on signup/sign-in. Better Auth sign-up.mjs:155-156,217-253 forces emailVerified=false and returns token:null; sign-in.mjs:332-353 checks password before revealing EMAIL_NOT_VERIFIED and refuses session creation for unverified users. Offline correct-password/unverified probe returned 403, requested mail, created no session. Existing tests/integration/auth-email.test.ts covers unverified refusal and verified login, but manually flips the DB boolean. Add a real signed verification-link flow and assert no cookie/protected access exists before verification; direct signup input cannot set emailVerified or role. Role/image over-posting outside these auth flags remains under the prior authorization/input audits.

3. Forged/expired verification tokens and replay after verification do not issue sessions. auth.ts:44 enables auto-sign-in only through Better Auth email-verification.mjs:175-181 (HS256/signature/expiry), 287-292 (already verified returns without session), 295-315 (first valid verification). JWT expiry defaults to one hour. Offline probes: bad and expired token 401; valid token for an already-verified fixture 200, zero writes/session calls. Add invalid/expired/replayed-link cases to the real-link regression in auth-email.test.ts. Tokens bind to email, not an opaque account id; no OAuth/change-email provider is enabled here. Do not describe email verification as a database-consumed reset token.

4. Password-reset tokens require a valid, unexpired, single-use server record. Better Auth password.mjs:73-79,125-127,149-167 uses a random 24-character alphanumeric token and one-hour expiry. internal-adapter.mjs:787-858 consumes atomically via adapter consumeOne and checks expiry; the Drizzle/Postgres adapter uses delete/returning for consumption. Offline handler rejected the second use when the consumed-token stub returned null. Atomic DB concurrency/expiry was source-reviewed, not exercised against a database. Existing auth-email.test.ts proves the happy reset/new-password login only. Add expired, reused and concurrent double-use cases; exactly one reset succeeds and the credential cannot be changed again with that token. Session revocation does NOT hold and is filed as 01M5A6NTZZ25Z46EJQ6F23G7B1.

5. Auth callback redirects and CSRF checks hold. App safeRedirectPath (src/lib/utils/urls.ts:12-26), used by sign-in/sign-up, rejects off-site redirect paths. Existing urls.test.ts and invite-sign-in.test.ts pin that app logic. Better Auth origin-check.mjs validates callbackURL/redirectTo and cookie-bearing POST Origin; sign-in also uses formCsrfMiddleware. Offline auth probes returned 403 for foreign Origin on change-password and external sign-in/reset callbacks. No disables/trusted-origin wildcard in auth.ts. Add a small auth configuration/handler regression that unauthorized Origin and callback URLs are refused before credential writes/email/session creation. Kit remote checks remain owned by the earlier lock-in.

6. Unknown email responses are generic. Wrong-password and unknown-user sign-in returned identical 401 JSON in offline probes; only a correct password reaches the unverified-account branch. Reset requests for existing and unknown fixtures returned identical 200 JSON. Anonymous verification resend returned {status:true} for both and took 503/505 ms, matching Better Auth email-verification.mjs:98-118's 500 ms floor. Signup source returns a fresh synthetic user for duplicate addresses with token:null, hashing the attempted password first; it does not disclose the stored user's name/id/verification status (sign-up.mjs:155-202). Existing auth-email.test.ts checks re-registration's UI message only. Extend it to compare API response shape/status and no session for duplicate/new signups; add offline API checks for unknown/wrong sign-in and known/unknown reset/resend. Timing limits: bcrypt is a filed gap; reset uses dummy random generation/read for missing users but real insert for existing users, so exact DB timing equality is not claimed or measured.

7. Mail delivery rejection does not become an existence-dependent auth error. src/lib/server/auth.ts:37-39,45-47 and email.ts:38-53,57-69 detach delivery and catch Mailgun rejection. A source-based isolated harness forced Mailgun messages.create to reject on reset, verification and sendEmail; all returned without throwing and logged the failure. Existing email.test.ts only covers console fallback; add rejected-provider tests with a synthetic configured key and a mocked client, including no unhandled rejection and prompt callback completion. The message-content test already belongs to 01M5A5B3PG61A9PBZ68BYZT3E2; do not duplicate it. No claim about full server logs being free of PII; delivery logs intentionally contain email addresses and console fallback contains token links.

8. Captcha cannot be bypassed by omitting the UI token while the secret is configured. auth.ts:12-25 protects /sign-up/email, /sign-in/email, /request-password-reset, /send-verification-email. Offline probes for sign-in: absent token 400 on canonical/trailing/repeated-slash paths; percent-encoded route spelling 404, not an unguarded handler; rejected challenge 403; network failure 500; malformed upstream data refused. The installed captcha plugin normalizes paths and fails closed. Cloudflare calls were mocked, never sent. App verifyTurnstile also refuses missing tokens, success:false and network failure (all existing turnstile.test.ts tests passed). Add a test of auth.ts's configured endpoint coverage with a synthetic enabled secret, asserting every listed endpoint refuses missing/rejected captcha before mail/auth writes; keep helper tests. Blank secret intentionally disables captcha even in production; passive widget presence establishes the public key only, not server-secret enablement. Cloudflare hostname/replay enforcement and actual deployed key settings were not checked.

9. Per-IP limits and /64 bucketing hold in the installed library. auth.ts leaves defaults: enabled in production, disabled in dev/test, in-memory per process; general 100/10s per path, sign-in/signup/change-password/change-email 3/10s, reset-request/resend 3/60s. Offline onRequestRateLimit calls with enabled=true: 200,200,200,429 for sign-in, reset-request, resend, change-password while rotating IPv6 host suffixes in one /64. IPv4-mapped IPv6 normalizes to the IPv4 bucket. Source: better-auth/dist/api/rate-limiter/index.mjs, context/create-context.mjs:170-175, @better-auth/core/dist/utils/ip.mjs. No bypass from changing an IPv6 host suffix. Prior deployed-IP verification: 01M4D4EAZ03YB416EKZJDSRF1K and decision 01M5A2XJC28ZGAW405A88YKK8E observed visitor /64 rather than proxy IP. This does not prove hostile forwarding headers are stripped or current production thresholds. No new unit suite for library internals; retain a documented offline upgrade check and have deployment review proxy topology/header sanitization. Account-deletion password throttling is already 01M57TCWXH5HG387VPHEDR8Y9Q.

10. Session cookie protections and expiry are present in the HTTPS configuration. Source plus actual offline sign-in response: __Secure-better-auth.session_token, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain, Max-Age=604800 (7d). cookies/index.mjs:23-64 and context/create-context.mjs:147-149 define defaults: renewal after one day, freshness one day, rememberMe=false has a nonpersistent cookie and one-day DB expiry. Session tokens are random 32-character strings, signed with the auth secret; cookie cache is disabled with this database configuration. get-session checks the database and expiry (session.mjs:155-162), sign-out deletes the session and expires cookies; therefore revoked sessions are not accepted from a stale cookie cache. Those last expiry/logout branches were source-reviewed only. Garbage cookie handling already belongs to the input/output lock-in. Add an isolated HTTPS auth-configuration regression checking emitted cookie flags/lifetime, and one real sign-out/expired-session rejection test to existing auth integration coverage. Actual deployed issuance/renewal was NOT observed: passive anonymous requests issue no cookie, so parent criterion 1 remains partially unverified.

Version caveat: package.json currently requests Better Auth ^1.7.8 while the installed better-auth and core report 1.7.7. This audit checked installed executable code; do not assume a deployment or refreshed install has the same implementation. Dependency/deployment audits should reconcile versions and recheck security-sensitive defaults when they change.
