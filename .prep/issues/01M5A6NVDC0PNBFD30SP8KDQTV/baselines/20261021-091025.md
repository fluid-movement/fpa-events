Authentication audit, 2026-10-19, parent 01M5A34XDWPGKSKMTVA213DHX7.

Vulnerability: failed sign-in uses different password work for unknown users and imported bcrypt accounts. Better Auth deliberately hashes a dummy password with the configured scrypt hasher for an unknown email, but src/lib/server/password.ts:17-21 verifies imported accounts with bcrypt at the stored cost. The failure body is identical, yet the work factor becomes a timing oracle for whether a candidate address belongs to a legacy account. The application has no equalization policy for these mixed hash families.

Where: src/lib/server/auth.ts:34-36 wires hashPassword (scrypt) and the mixed verifier together; src/lib/server/password.ts:6,17-21 dispatches bcrypt by prefix; installed Better Auth 1.7.7 node_modules/better-auth/dist/api/routes/sign-in.mjs:318-337 hashes on missing account/password and verifies on an existing account. Successful bcrypt sign-in never rewrites the hash, so this distinction does not age out automatically.

Reproduction class: in an isolated fixture test, compare repeated incorrect-password sign-ins for an unknown address and synthetic existing accounts with scrypt and supported bcrypt costs. No real user addresses, accounts, database rows or live attack traffic are needed. The audit measured the actual hashing functions for 12 sequential samples per case: unknown-user scrypt hash median 58.4 ms (57.6-60.2), existing scrypt verify 57.7 ms (57.1-58.6), bcrypt cost 10 70.3 ms (69.1-70.4), bcrypt cost 12 278.5 ms (276.1-281.6). API probes with adapter stubs confirmed identical 401 responses and the source confirms those exact hash branches. These are local algorithm timings, not measured deployed enumeration accuracy. The audit did not inspect production hash costs or bypass production captcha/rate limits.

Severity: low. Go-live recommendation: non-blocking follow-up; captcha and per-IP throttling constrain sampling, and the address only becomes distinguishable when its legacy cost differs sufficiently. This does not reveal passwords. Unknown/new scrypt accounts were not reliably distinguished by these local hash timings.

Fix: implement a bounded failed-authentication work/timing policy that reduces distinguishability across the supported legacy costs and unknown accounts, retaining rate limits and denial-of-service bounds. Transparent rehash after successful legacy login may help retirement, but by itself does not protect accounts that have not signed in. Rehash-on-login is not an existing agreed project requirement; do not silently expand the compatibility feature into one.
