All in `src/lib/error-tracking.ts` and its test `src/lib/error-tracking.test.ts` (read both first; the decision is /decisions/01M57R12DXKFJBJPPTFW5G6M2B.md). `scrubEvent` already runs each step in its own guarded block and fails closed; follow that pattern for the new steps and keep the module free of server-only imports (it is shared with `hooks.client.ts`). The live event shape (what GlitchTip showed for a server error): tags `errorId, os.name, release, environment, server_name`; contexts `os, app, trace, device, culture, runtime, cloud_resource`; `exception.values[].mechanism` `{type, source, handled, parent_id}` with optional `data`. The browser SDK adds its own tags and contexts (browser, url-related ones); keep `browser`/`browser.name` tags and the `browser` context only if they hold no URL or user text, and drop the rest. Prefer one allowlist constant per field group, named and commented, so adding a field later is a one-line, reviewed change. Unit tests: events with extra tags and contexts and a Postgres-shaped `mechanism.data.detail` (must be gone, `code` kept), the kept fields survive untouched, null and non-object events return a safe empty result instead of throwing, non-string `transaction`/`release`/`environment` are dropped. No database or browser involved: run `npm run check`, `npm run test`, eslint and prettier only. After deploy the orchestrator repeats `GET /events/%00` and reads the event through the GlitchTip MCP.
