Severity: low (documentation that misdirects deploy and audit checks; no vulnerability). Go-live recommendation: does not block go-live, but fix it before the next dependency-changing release, because the engines check it tells people to run uses the wrong Node.

## Problem

Decision /decisions/01M59PK8QMF1B7Z8BMMDMD6PH5.md (user, 2026-10-19) pins NIXPACKS_NODE_VERSION to 24 in Coolify. README.md:177 points to it. But:

- AGENTS.md, Quality gates, still says the deploy runs Node 22.19.0 / npm 10.9.3 at NIXPACKS_NODE_VERSION=22, and its engines one-liner hard-codes '22.19.0'.
- .npmrc:1-19 explains the missing engine-strict with the Node 22.19.0 build and recommends pinning to 24 as a future step.

This audit was itself briefed with "nixpacks on Node 22" from that text.

## What the engines check shows (lock SHA256 985daa23...)

- At 22.19.0 and 22.22.1: no package in package-lock.json fails its engines range.
- At 24.0.0: only vite-plus 0.2.9 and @voidzero-dev/vite-plus-core 0.2.9 fail (`^20.19.0 || ^22.18.0 || >=24.11.0`). Both are dev-only and not used by `npm run build` (plain `vite build`) or `node build`; without engine-strict npm only warns.
- At 24.11.0 and the local 24.22.0: nothing fails.
- tools/migrate: nothing fails at 22.19.0 or 24.0.0 (its own engines: >=22).
- @sveltejs/kit 3.0.0 requires >=22.17, matching package.json engines.

So the app is safe on any Node 24 that nixpacks resolves; the stale text is the problem, plus the major-only pin means nobody records which patch is actually running.

## Fix

Update AGENTS.md Quality gates and the .npmrc comment to the Node 24 decision, make the engines one-liner take the deployed version as a parameter, and record the deployed `node -v` (from the deploy log) wherever the docs name it. Whether engine-strict comes back is the user's call; the .npmrc comment itself says it could once the build is on 24.
