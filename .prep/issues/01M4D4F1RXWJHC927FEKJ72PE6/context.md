Decision: /decisions on this issue (prep knowledge find account deletion): events the user created are deleted even with co-organizers; no ownership transfer. Only the pictures are missing.

`deleteAccount` in `src/routes/settings/account/data.remote.ts` runs `db.delete(events).where(eq(events.userId, signedIn.id))` and never touches R2. `deleteEvent` (find it with `grep -rn releasePicture src`) calls `releasePicture(url, eventId)` from `src/lib/server/eventForm.ts`, which deletes the object unless another event still points at the same URL and swallows R2 errors (best-effort). Do the same here: read the `id` and `picture` of the user's events before deleting them, delete the rows as now, then call `releasePicture(picture, id)` for each event with a picture. Release after the row delete, so a failing R2 call can never block the account deletion and so pictures shared by two of the user's own events are still removed (the shared-picture check then sees no remaining reference). A picture shared with another user's event must stay. Keep the order of the existing deletes and the password check untouched (merged by the password issue; the field is `_password`). Do not change anything else in the function.

Tests (destructive, hard to undo): an integration test in `tests/integration/` using a throwaway account from `signUpAndSignIn()` (never the shared storageState user), plus a unit test if the logic is extracted. R2 keys are blank in `.env.test`, so check how `deleteImage` behaves with the dev fallback in `src/lib/server/r2.ts` and assert through that path (for example by stubbing at the module boundary in a unit test of the release step) rather than a real bucket.
